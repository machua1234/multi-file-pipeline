# Day 2 – Multi-File Data Processing Pipeline

Squad Python Specialization – Data Engineering

A Python pipeline that reads daily transaction CSV files, validates them, and combines the clean rows into one dataset. Bad rows go to a rejects file with the reasons they failed, and a processing summary is printed and saved at the end.

## Project structure

```
multi-file-pipeline/
├── pipeline.py                      # the pipeline code
├── data/                            # input files
│   ├── transactions_2026-10-01.csv

│   └── transactions_2026-10-03.csv
├── docs/

├── output/                          # generated by the pipeline
│   ├── consolidated_transactions.csv
│   ├── rejected_transactions.csv
│   └── summary.txt
└── README.md
```

## Requirements

- Python 3.10+ (developed on 3.14)
- Standard library only (`argparse`, `csv`, `datetime`, `logging`, `pathlib`). No pandas.

## Usage

```bash
python pipeline.py --input data/ --output output/
```

Both options are optional and default to `data/` and `output/`.

## How it works

| Step | Function | What it does |
|------|----------|--------------|
| 1 | `discover_files()` | Finds `transactions_*.csv` with `pathlib` and sorts them by filename. The names contain ISO dates, so this is also date order. |
| 2 | `read_transactions()` | Reads a file with `csv.DictReader` and tags every row with `source_file` and `row_number`. |
| 3 | `apply_aliases()` | Renames known alias columns (`qty` → `quantity`) and logs each rename. |
| 4 | `validate_columns()` | Set difference `required - set(header)` gives the missing required columns. |
| 5 | `find_problems()` | Returns every reason a row is invalid. |
| 6 | `clean_row()` | Strips whitespace, converts numbers to `int` and adds `line_total`. |
| 7 | `write_csv()` | Writes the CSV with `csv.DictWriter`, creating the output folder if needed. |
| 8 | `build_summary()` | Formats the summary, which is printed and saved to `output/summary.txt`. |
| – | `run_pipeline()` / `main()` | Runs all the steps and handles the command-line options. |

### Required columns

`transaction_id`, `date`, `branch`, `customer_id`, `product`, `quantity`, `unit_price`, `payment_method`

`payment_ref` is optional (cash sales leave it blank).

### Row validation: `find_problems(row, seen_ids)`

It returns **every** reason a row is invalid, so one row can have several. Each reason starts with a fixed prefix so the summary can count it:

- `missing value: <col>`: a required field is blank or only whitespace.
- `invalid number: ...`: `quantity` or `unit_price` is not a whole number, or is not greater than 0. A blank value is reported only as missing, not twice.
- `duplicate ID: <id> already seen`: `seen_ids` is created once per run and shared across all files, so repeats in later files are caught. The **first** copy of an ID is kept, and every later copy is rejected.

### Cleaning: `clean_row(row)`

No pandas: it uses plain dicts, a set and comprehensions.

- A **dict comprehension** keeps only the output columns and strips whitespace from every value.
- A loop over the **set** `INT_COLUMNS` (`quantity`, `unit_price`) converts those values to `int`.
- It adds `line_total = quantity × unit_price` and returns the keys in output-column order.

## Design decisions

### Files with a wrong header: map known aliases, reject everything else

`transactions_2026-10-03.csv` uses `qty` instead of `quantity`.

**Decision:** known aliases listed in `COLUMN_ALIASES` (currently `{"qty": "quantity"}`) are renamed to the standard column name before the header is checked. If a file is **still** missing a required column after that, the **whole file is rejected**. It is reported under "Files with column issues", and all of its rows go to the rejects file with the reason `column issue: file missing <columns>`.

**Why map known aliases:**
- `qty` clearly means `quantity`. Its values are whole numbers in the same position, and the rest of the file matches the schema. Rejecting the file would throw away 12 transactions, 10 of them valid (KES 6,860 of revenue), over a naming difference.
- Upstream systems often rename columns (a new POS version, a different branch export). Mapping lets the pipeline keep running and still records what happened through the logged warning.
- After mapping, the rows still go through every row-level check. Real problems in that file are still caught: TXN-1029 (duplicate) and TXN-1035 (quantity of -4).
- A rename is only applied if the standard column isn't already present, so real data is never overwritten.

**Why reject the whole file in every other case:**
- Guessing what an unknown column means risks quietly loading wrong data. That's worse than loading nothing, because the error ends up in revenue figures without anyone noticing.
- If a required column is missing, every row in the file would fail anyway. Rejecting at file level gives one clear message instead of the same error on every row.
- The allow-list is explicit. Adding a new alias is a deliberate one-line change that someone reviews.

### Extra columns

Extra columns (e.g. `cashier`) are allowed and don't make a file fail. They are not part of the consolidated output, but they are kept in the rejects file so rejected rows stay complete.

### Nothing disappears

Every row that is read ends up in exactly one of the two CSVs. Rows from rejected files are counted too. `run_pipeline()` raises an error if `accepted + rejected != rows read`, so a lost row can't go unnoticed.

### Summary counts

The rejection breakdown counts **rows** per category. A row with problems in two categories is counted in both, and the summary adds a note if that ever makes the breakdown add up to more than "Rows rejected". On the current data there's no overlap: 4 + 2 + 3 = 9.
